## 1. Что ломалось у Павла и почему

Экран "Ход дела" (из DESKTOP_017_A) сам по себе не падает - демон (`qwen serve`)
стартует и отвечает на `/health` независимо от того, заполнены ли
`DOVOD_API_BASE`/`DOVOD_API_KEY`/`DOVOD_MODEL` в `~/.qwen/.env`. Падение происходило
на шаге позже: как только юрист нажимал кнопку шага "в переписке" (Опись, Позиция,
Проект документа, Сверка) или "Открыть переписку с Доводом", `open_chat` переводил
окно на веб-страницу переписки (`packages/web-shell`), и там попытка создать сессию
агента с незаполненным/неразрешённым `${DOVOD_MODEL}` падала технической ошибкой
"agent channel closed during initialize" (packages/web-shell/client/daemon/session/
actions.ts, не наш узкий контур для правки по CLAUDE.md §1 - там наследная логика
протокола агента, не продуктовый экран).

Правильное место правки - граница desktop-shell перед тем, как окно вообще
переходит на страницу переписки, а не глубина web-shell.

## 2. Экран "Введите код доступа"

`src-tauri/src/main.rs`: новая функция `config_ready(app)` - true, если код доступа
уже введён в этом запуске (`ApplicationState.access_credentials`), либо
`~/.qwen/.env` уже вручную заполнен тройкой `DOVOD_API_BASE/KEY/MODEL` или
`OPENAI_BASE_URL/API_KEY/MODEL` (путь из README dovod/, остаётся рабочим).
Команда `open_chat` теперь сначала проверяет `config_ready` и, если настройки не
полные, возвращает `Err("access-code-required")` - НЕ запуская переход на страницу
переписки и НЕ трогая демон. Сессия агента физически не стартует.

`packages/desktop-shell/bootstrap/index.html` и `bootstrap.js`: новый экран `#access`
("Нужен код доступа", поле ввода, кнопка "Войти", подсказка обратиться к тому, кто
выдаёт доступ). `runInChat()`/`openChat()` в bootstrap.js ловят строго строку
`'access-code-required'` (сверено с константой `ACCESS_CODE_REQUIRED` в main.rs) и
показывают этот экран вместо технической ошибки - юрист никогда не видит
"agent channel closed" и окно не падает.

По ходу найден и исправлен баг в черновике: при пустом коде `submitAccessCode()`
выставлял текст ошибки, но не делал абзац видимым (`style.display` оставался
не тронут, CSS прячет абзац по умолчанию) - юрист не увидел бы вообще никакой
реакции на пустое поле. Исправлено; закреплено тестом (см. ниже).

## 3. Код доступа -> сервер выдаёт доступ к модели

В репозитории не нашлось никакой уже заложенной схемы "код доступа -> сервер"
(искал access code, proxy, api.dovod.law, DOVOD_ACCESS_SERVER - по всей
packages/desktop-shell и packages/web-shell) - нынешняя `settings.template.json`/
`env.template` знают только про ручное заполнение `.env`. Сделана клиентская часть:

- Новая команда `submit_access_code(code)`: адрес сервера - `resolve_access_server()`
  - сначала переменная окружения процесса `DOVOD_ACCESS_SERVER` (для разработки), а
  иначе та же `~/.qwen/.env`, что и остальные три значения (добавлена новая
  необязательная строка `DOVOD_ACCESS_SERVER` в `dovod/env.template` с комментарием).
  Первая версия правки проверяла только переменную окружения процесса - для
  установленного у пользователя приложения это недостижимо (нет способа выставить
  переменную окружения для GUI-процесса на обычной Windows-машине), поэтому
  добавлен путь через `.env`, который владелец может заполнить заранее через свой
  установщик, без пересборки.
- `redeem_access_code(endpoint, code)`: код уходит как query-параметр
  `GET <endpoint>?code=<код>` (не POST с телом) - осознанный выбор: крейт `ureq` в
  этом Cargo.toml собран с `default-features = false` (без фич "json"/TLS-бэкенда
  для send/send_json), а GET с `.call()`/`.into_body().read_to_string()` - ровно тот
  же приём, что уже скомпилирован и работает в `runtime.rs::wait_for_health`. Ответ
  ожидается JSON `{"api_base": "...", "api_key": "...", "model": "..."}` (разобран
  вручную через `serde_json::Value`, не через фичу ureq) либо `{"error": "..."}`
  при отказе.
- Три значения кладутся в `ApplicationState.access_credentials` (только в памяти
  этого запуска приложения, НЕ в `~/.qwen/.env` - требование задания "ключ модели не
  хранить у пользователя") и едут прямиком в окружение процесса демона при
  следующем (пере)запуске: `runtime.rs::DesktopRuntime::start` принимает новый
  параметр `extra_env: &[(String, String)]`, `start_runtime_async` собирает его из
  `access_credentials` перед каждым запуском.
- Имя модели и провайдер не хардкодятся нигде - всё так же приходит либо из
  `.env`, либо с сервера; выбор провайдера не делался (задание прямо просило не
  выбирать - решение у владельца).

### Что нужно на сервере (владельцу, для будущей сессии)

- Один GET-эндпоинт по адресу из `DOVOD_ACCESS_SERVER` (полный адрес ручки целиком,
  например `https://api.dovod.law/v1/access`, не только домен).
- Принимает `?code=<код>`.
- Отвечает JSON `{"api_base": "...", "api_key": "...", "model": "..."}` при
  принятом коде, либо `{"error": "человеко-читаемая причина"}` (или любой другой
  статус/тело) при отказе - текст из `error` попадает на экран как
  "Код не принят: <текст>", так что он должен быть пригоден для показа юристу
  без дополнительного перевода.
- Код должен быть одноразовым или ограниченным по времени на стороне сервера -
  клиент не делает это сам, просто передаёт то, что ввёл юрист.
- HTTPS: клиентский крейт `ureq` в этой сборке собран без TLS-фич
  (`default-features = false`, см. Cargo.toml) - запрос к `https://` адресу сейчас
  упадёт ошибкой на этапе соединения ("Не удалось связаться с сервером доступа"),
  не на этапе компиляции. Прежде чем такой сервер появится, нужно отдельно
  добавить TLS-фичу ureq (например `rustls`) в `src-tauri/Cargo.toml` и
  перепроверить сборку в CI - это не сделано в этой сессии: без cargo в этой
  оболочке я не мог проверить, что добавление фичи компилируется, а блок задания
  не требовал реального сервера здесь и сейчас.
- Сам сервер не трогал, как и просило задание.

## 7. Оценка: сервер-прокси вместо выдачи ключа провайдера (по просьбе владельца)

Замечание владельца справедливо: сейчас `redeem_access_code` получает от сервера
доступа настоящий `api_key` провайдера модели и держит его в памяти приложения
(`ApplicationState.access_credentials`), а затем передаёт в окружение процесса
демона (`DesktopRuntime::start`). Даже без записи на диск это реальная
поверхность: системный процесс с нужными правами может прочитать переменные
окружения чужого процесса, сам демон логирует свой stdout/stderr в
desktop-runtime.log (`runtime.rs::append_log`) - если qwen-code или модельный
клиент внутри него случайно залогируют заголовки запроса при ошибке, ключ может
попасть в этот журнал. Это не теоретическая мелочь при утечке журнала или памяти.

Альтернатива - сервер сам проксирует запросы к модели, клиент шлёт запросы на
наш адрес с кодом доступа, настоящий ключ провайдера никогда не покидает сервер:

- Что меняется на клиенте: по сути ничего в коде. Текущая схема уже устроена
  как "сервер решает, что отдать в api_base/api_key/model" - `settings.
  template.json` и так обращается к ним как к обычному OpenAI-совместимому
  провайдеру (`baseUrl`, `envKey`), не делая разницы между "настоящий адрес
  провайдера" и "наш прокси". Если сервер возвращает `api_base` = адрес СВОЕГО
  прокси (например `https://api.dovod.law/v1/model`), а `api_key` = не
  настоящий ключ провайдера, а свой собственный токен (например тот же код
  доступа или отдельно выданный короткоживущий токен, который сервер умеет
  проверять и привязывать к лимитам), клиент работает ровно так же - просто
  шлёт этот токен как Bearer-заголовок на наш адрес вместо адреса провайдера.
  `redeem_access_code`/`AccessCredentials`/`DesktopRuntime::start` не нужно
  трогать вовсе: они уже агностичны к тому, что именно сервер прислал в эти
  три поля.
- Что всё же стоит добавить (не в этой сессии): если сервер выдаёт
  короткоживущий токен (а не сам код доступа как постоянный токен), при его
  истечении модельные запросы начнут падать 401 без автоматического
  повторного обмена - сейчас в клиенте нет пути "перевыдать токен без участия
  юриста". Простой вариант без усложнения: пусть сервер принимает тот же
  код доступа как `api_key` на каждый запрос к прокси (без отдельного обмена
  на временный токен) - тогда это не нужно, но тогда сам код доступа должен
  быть достаточно длинным/непредсказуемым, чтобы служить секретом сам по себе.
- Остаточный риск не исчезает полностью даже с прокси: токен (будь то код
  доступа или временный токен) всё равно живёт в памяти процесса и в
  окружении демона тем же способом, что и сейчас - просто его компрометация
  вредит меньше (сервер может его отозвать/ограничить по лимиту и времени,
  в отличие от настоящего ключа провайдера, который отозвать может только
  сам провайдер).
- Итог: архитектурно прокси - однозначно лучше и ПОЧТИ не требует изменений
  на клиенте (только то, что сервер присылает в ответе), но не делал эту
  правку - задание прямо попросило только оценку, не реализацию.
