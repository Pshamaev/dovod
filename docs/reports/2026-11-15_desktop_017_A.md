## 1. Первый запуск: приветствие и демо-дело

`src-tauri/src/main.rs`: раньше `setup_app` при отсутствии сохранённого дела сама
создавала и поднимала папку `~/Documents/Довод` (функция `initial_workspace` +
`default_workspace`). Теперь на первом запуске ничего не создаётся и не
поднимается: `saved_workspace()` возвращает `None`, оболочка остаётся на экране
приветствия (`#welcome` в bootstrap/index.html), и дело выбирает юрист одной из
двух кнопок - "Открыть дело" или "Попробовать на учебном деле".

Демо-дело: новая команда `open_demo_case`. Источник - `_demo/ДТП_демо` внутри
пакета конвейера (`runtime/qwen-code/dovod-tools/_demo/ДТП_демо`, см.
`demo_case_source()`), копируется в `~/Documents/ДТП_демо (демо)/для_модели`
(`copy_directory()`, без перезаписи существующих файлов - повторное открытие не
стирает правки юриста в демо-деле). Кнопка демо скрывается сама, если в собранном
пакете демо-дела нет (`demoAvailable` в `bootstrap_state`) - на машине без
собранного pipeline-пакета (сейчас, без доступа к CI) это не проверить вживую.

## 3. Ход дела: шаги кнопками

`#case` в bootstrap/index.html, список `STEPS` в bootstrap.js: шесть шагов -
Подготовить материалы, Опись, Позиция, Проект документа, Сверка, Собрать
результат. У каждого состояние словами (`setStepState`): "ещё не начато,
примерно N минут", "идёт, примерно N минут" / "идёт в переписке, примерно N
минут", "готово", "нужна ваша подпись", "не получилось, можно повторить".

Два вида шагов:
- "сам" (Подготовить материалы, Собрать результат) - оболочка вызывает
  `dovod_prompts.exe` напрямую через новую команду `run_case_step` (Rust:
  `pipeline_arguments()` сопоставляет шаг экрана с теми же подкомандами, что в
  `dovod/commands/*.toml`: `prepare-run`, `restore-run`; логика конвейера не
  дублируется, вызывается тот же exe).
- "переписка" (Опись, Позиция, Проект документа, Сверка) - оболочка открывает
  переписку (`open_chat`), где эти шаги идут командами `/dovod:*`, как и раньше.

## 4. Автопилот

Кнопка "Пройти дело" (`runAutopilot`): идёт по списку шагов по порядку, каждый
шаг запускает либо `run_case_step`, либо открывает переписку. Останавливается на
двух подписях (`SIGNATURES` в bootstrap.js, см. ниже), на любой ошибке шага и
когда все шаги пройдены (экран результата). Можно и нажимать шаги по одному -
кнопки шагов не блокируются автопилотом.

### Подписи
- После "Опись": "Проверьте, что уходит из дела" - кнопка "Показать, что уходит
  из дела" вызывает тот же `eyecheck` через `run_case_step`, что команда
  `/dovod:eyecheck`; кнопка "Подтверждаю, продолжить" снимает подпись и
  продолжает автопилот с этого шага.
- После "Собрать результат": "Подпишите итоговый проект" - читает готовый
  проект (путь к документу), подтверждение запускает `restore-run`.

Rust: `open_chat` - окно остаётся на экране "Ход дела", пока юрист сам не
попросит переписку (`open_chat_when_ready` в `ApplicationState`,
`start_runtime_async` проверяет этот флаг перед навигацией на `authenticated_
web_url()`). Это меняет прежнее поведение (окно сразу переходило в переписку
после старта демона) - сделано намеренно по пункту 4 задания.

## Правка после первой сборки: E0597 в run_case_step (push 3 из 3)

Сборка установщика из `dovod-017` (коммит `b75d66a013`, прогон 43687099120)
упала на шаге `tauri build`, на компиляции Rust, одной ошибкой:

```
465 |             lock(&state.last_workspace).clone(),
    |             ------^^^^^----------------
    |             |     borrowed value does not live long enough
    |     `state` dropped here while still borrowed
error[E0597]
```

Место: `src-tauri/src/main.rs`, функция `run_case_step` (моя правка шага 6).
Состояние читалось в блоке, чтобы `State<'_, ApplicationState>` не жил через
`await`, и последним выражением блока шёл вызов `bootstrap_workspace`, внутри
которого `lock(&state.last_workspace).clone()`. Временные значения последнего
выражения блока уничтожаются позже локальных переменных этого блока, поэтому
`state` уже уничтожен, а `MutexGuard` на его поле ещё жив.

Исправлено: `last_workspace` и `persisted_workspace` читаются в локальные
переменные, в последнем выражении блока остаётся только вызов
`bootstrap_workspace` с владеющими значениями. Блок сохранён - `state`
по-прежнему не живёт через `await` в `spawn_blocking`.

Проверка на те же случаи в остальном коде (cargo на машине владельца нет,
компиляцию локально проверить нельзя, поэтому проверка глазами по всем
