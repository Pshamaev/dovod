## 1. Архитектура упаковки

### 1.1. Как устроена поставка сейчас (опора для решения)

- `packages/desktop-shell/src-tauri/tauri.conf.json:35-37`: в установщик уже кладётся
  целое дерево папок через `bundle.resources`: `"../runtime/qwen-code": "runtime/qwen-code"`.
- `packages/desktop-shell/scripts/prepare-runtime.js` собирает это дерево: бандл CLI в
  `lib/`, папку `dovod/` с шаблонами, `dovod-entry.js` в `lib/`, и **скачивает Node.js с
  nodejs.org, сверяет SHA256 по SHASUMS256.txt, распаковывает в `node/`** (строки 128-186,
  241-268). То есть в проекте уже есть рабочий образец "сторонний интерпретатор едет внутрь
  установщика": скачивание, проверка контрольной суммы, распаковка, кеш, запись
  `checksums.json` по всему дереву (строка 327).
- `packages/desktop-shell/src-tauri/src/runtime.rs:165-200`: `RuntimeLayout::resolve`
  находит корень как `resource_dir()/runtime/qwen-code` в релизе, как
  `<манифест>/../runtime/qwen-code` в отладке, с перебивкой через
  `QWEN_DESKTOP_RUNTIME_DIR`, и снимает префикс `\\?\` через dunce.
- `scripts/smoke-runtime.js` проверяет целостность дерева по `checksums.json` перед
  запуском демона; в CI это шаг `npm run smoke:runtime`
  (`.github/workflows/desktop-release.yml:403-405`).

### 1.2. Где собирается Python-часть

**В репозитории garant-bot, в его собственном CI, на windows-latest.** Обоснование:
CLAUDE.md §1 прямо запрещает копировать код конвейера сюда, а PyInstaller нужно запускать
там, где лежат исходники и requirements. Собирать конвейер в репозитории Довода без его
исходников невозможно иначе как через копирование, то есть нарушением правила.

**PyInstaller onedir, не onefile.** Обоснование не вкусовое:

1. onefile при каждом запуске распаковывает весь архив в `%TEMP%\_MEIxxxxxx`. С моделями
   OCR (ONNX RapidOCR плюс `rus.traineddata`) это десятки или сотни мегабайт на каждый
   вызов команды. Команды `/dovod:*` вызываются многократно за сессию
   (`packages/desktop-shell/dovod/commands/*.toml` - семь команд, каждая запускает процесс
   заново), и распаковка легла бы в задержку каждой из них.
2. onefile плохо живёт с антивирусами и SmartScreen: распаковка исполняемого кода в TEMP
   при каждом старте - типовой триггер. Установщик и так будет неподписанным или
   подписанным не сразу (`desktop-release.yml:311-345` допускает unsigned с
   предупреждением), лишний триггер не нужен.
3. onedir ложится в уже существующий механизм: дерево файлов, покрытое `checksums.json`
   и проверяемое `smoke:runtime`. Внутренности onefile проверить таким способом нельзя.
4. Tesseract всё равно поедет отдельной папкой (он вызывается как внешний exe, а не
   импортируется), то есть "один файл" не получается в принципе.

### 1.3. Как Python-часть попадает в установщик Tauri

**Через `bundle.resources`, не через `externalBin`.** Обоснование:

- `externalBin` в Tauri 2 рассчитан на одиночные sidecar-бинарники, которые кладутся с
  суффиксом целевой тройки (`имя-x86_64-pc-windows-msvc.exe`) и копируются по одному файлу.
  Дерево onedir (exe плюс `_internal` с DLL, pyd и файлами данных) так не переносится:
  Tauri скопирует только названный файл, и бинарник не найдёт своё окружение.
- `resources` уже работает в этом проекте именно для дерева с интерпретатором внутри
  (`runtime/qwen-code` с `node/node.exe`), то есть путь проверен на практике, включая
  разрешение пути в релизе и в отладке.

**Конкретное место: `packages/desktop-shell/runtime/qwen-code/dovod-tools/`.** Не
`runtime/dovod-tools` рядом, а внутрь существующего корня. Причина: `writeChecksums()`
(`prepare-runtime.js:327-341`) обходит только `packageRoot`, то есть `runtime/qwen-code`.
Папка-сестра осталась бы без контрольных сумм и без проверки в `smoke:runtime`, пришлось бы
писать второй механизм. При вложении внутрь не меняется ни запись в `bundle.resources`, ни
`RuntimeLayout`, а целостность конвейера проверяется тем же шагом CI, что и целостность
Node. Имя папки `qwen-code` на экранах пользователя не появляется (см. пункт 6), это
внутренний путь; переименование корня - отдельная правка, не этого шага.

Что для этого нужно в `prepare-runtime.js`: шаг рядом с `bundleDovodResources()` (строка
288), который скачивает артефакт сборки конвейера, сверяет SHA256 по приложенному файлу
сумм и распаковывает в `dovodToolsDir`. Весь нужный код уже есть и переиспользуется как
есть: `download()` (241), `verifyChecksum()` (249), `extractNodeArchive()` через `tar -xf`
(266), `copyDirectory()` (353). Проверка обязательности: добавить `dovod-tools/dovod_run.exe`
в список `required` (строки 70-80) и в `smoke-runtime.js`, чтобы сборка падала, а не
выпускала установщик без конвейера.

### 1.4. Как CI получает конвейер из закрытого репозитория

**Выбор: приватный GitHub Release в garant-bot плюс скачивание по токену в сборке Довода.**

Как это работает:

1. В garant-bot появляется свой workflow (`dovod-tools-build.yml`), который по
   `workflow_dispatch` собирает PyInstaller onedir на windows-latest, пакует в
   `dovod-tools-<версия>-win-x64.zip`, считает SHA256 и публикует оба файла как ассеты
   релиза с тегом `dovod-tools-v<версия>` в своём приватном репозитории.
2. В Доводе в `desktop-release.yml` добавляется вход `dovod_tools_tag` и шаг, который
   делает `gh release download "$DOVOD_TOOLS_TAG" --repo <owner>/garant-bot` с токеном из
   секрета репозитория Довода (fine-grained PAT, права только Contents: read только на
   garant-bot). Путь к распакованному дереву передаётся в `prepare-runtime.js` переменной
   окружения (по образцу `QWEN_CODE_ROOT` и `QWEN_DESKTOP_NODE_CACHE_DIR`), а не
   скачиванием изнутри скрипта, чтобы токен не попадал в скрипт сборки.

Почему не остальные варианты:

- **Артефакт сборки (actions/upload-artifact) из garant-bot.** Отклонено: артефакты
  привязаны к конкретному прогону, живут ограниченный срок (здесь 14 дней,
  `desktop-release.yml:554`) и доступны по `run_id`, который надо где-то хранить.
  Пересобрать установщик 0.1.6 через полгода стало бы невозможно. Релиз с тегом
  воспроизводится.
- **git submodule на garant-bot.** Отклонено по двум причинам. Первая: submodule кладёт в
  дерево Довода указатель на закрытый репозиторий, и любая сборка требует прав на чтение
  исходников конвейера, то есть исходники конвейера фактически становятся частью сборки
  Довода, против духа CLAUDE.md §1. Вторая: в submodule приедут исходники, а не собранный
  onedir, значит PyInstaller пришлось бы запускать в CI Довода вместе с установкой Python и
  всех зависимостей конвейера, и состав зависимостей конвейера стал бы частью сборки
  Довода. Выбранный вариант отдаёт готовое дерево и не знает, из чего оно собрано.

Про секреты: сам конвейер секретов не содержит, а вот `citationServer.js` читает `.env`
бота (поэтому по решению владельца в 0.1.6 он не поставляется). Токен скачивания живёт
только в секретах репозитория Довода и в одном шаге CI.

### 1.5. Куда пишутся рабочие данные при первом запуске

В установочную папку не пишется ничего: при обновлении она заменяется целиком, а
`checksums.json` любую запись туда превратит в падение `smoke:runtime`.

Что уже так и устроено в коде:

| Что | Куда | Код |
| --- | --- | --- |
| Настройки, .env, команды `/dovod:*` | `%USERPROFILE%\.qwen` (перебивка `QWEN_HOME`) | `dovod/dovod-entry.js:32-47`, `seedDovod` 211-260 |
| Состояние окна | `%APPDATA%\law.dovod.desktop\desktop-state.json` | `src-tauri/src/desktop_state.rs:144-149` |
| Журнал демона | `%LOCALAPPDATA%\law.dovod.desktop\logs` | `scripts/resolve-log-root.js:11-21` |
| Данные дела | сама папка дела (рабочая папка процесса) | `src-tauri/src/runtime.rs:63, 536-550` |

Отдельно про Program Files: установщик собран с `"installMode": "currentUser"`
(`tauri.conf.json:57`), то есть NSIS ставит в `%LOCALAPPDATA%`, а не в Program Files, и
прав администратора не требует. Это снимает вопрос прав на запись, но не отменяет правила
выше: писать в установочную папку нельзя всё равно, из-за замены при обновлении.

Что нужно доделать в 0.1.6 для Python-части:

- Кеши и временные файлы конвейера направить в `%LOCALAPPDATA%\law.dovod.desktop\cache`
  переменными окружения, выставляемыми при запуске демона (`runtime.rs:65-66` уже
  выставляет `QWEN_CODE_DESKTOP` и `QWEN_SERVER_TOKEN`, туда же добавляются переменные
  конвейера). Критично для RapidOCR и onnxruntime: по умолчанию они ищут и складывают
  модели рядом с собственным пакетом, то есть внутри установочной папки.
- `DOVOD_TOOLS` перестаёт быть полем для пользователя. Сейчас `env.template` просит
  вписать путь к garant-bot руками, а `resolveDovodTools()`
  (`dovod/dovod-entry.js:69-81`) при пустом значении оставляет токен `__DOVOD_TOOLS__` в
  командах. В 0.1.6 значение по умолчанию должно приходить из resource_dir, иначе на чистой
  машине все семь команд приедут с неподставленным токеном.
- `TESSDATA_PREFIX` указывается на поставляемую папку tessdata, иначе Tesseract полезет
  искать её по реестру и не найдёт.

### 1.6. Чего в архитектуре пока нет (найдено по коду, не входило в вопросы)

- **Рабочая папка не сужена до `для_модели`.** `choose_workspace`
  (`src-tauri/src/main.rs:303-326`) открывает системный выбор папки
  (`blocking_pick_folder`) и передаёт выбранное в `--workspace` как есть
  (`runtime.rs:536-550`). Ограничение папкой `для_модели` сейчас обеспечивает только сам
  `dovod_run.py`. По CLAUDE.md §2 оболочка не должна открывать агенту корень дела, значит в
  0.1.6 `choose_workspace` должен выбирать дело и подставлять `<дело>\для_модели`
  (создавая её при необходимости), а не отдавать выбранную папку напрямую.
- **Вызов конвейера меняется с `python скрипт.py` на `exe`.** Все семь команд зовут
  `!{python "__DOVOD_TOOLS__\dovod_prompts.py" ...}`
  (`dovod/commands/*.toml`), а в поставке интерпретатора `python` не будет. Строки команд и
  правила `permissions.allow` в `dovod/settings.template.json:22-25` переписываются на
  `dovod_prompts.exe`. Важно: правила там намеренно без подстановочных знаков, потому что
  режим AUTO вырезает wildcard-правила для интерпретаторов как опасные (комментарий
  `dovod-entry.js:175-180`); у замороженного exe этой проблемы нет, но правило всё равно
  остаётся литеральным с подставленным путём.
- **`mcp-server.template.json` сам себя отключает при пустом `DOVOD_TOOLS`**
  (`dovod-entry.js:116-131`: при неразрешённом токене или `command: "PLACEHOLDER"` сервер
  не регистрируется). Если `DOVOD_TOOLS` начнёт разрешаться автоматически (см. 1.5), это
  предохранитель отключится и проверка ссылок зарегистрируется с путём внутрь поставки, где
  `citationServer.js` нет. Для 0.1.6 правильнее явно поставить в шаблоне
  `"command": "PLACEHOLDER"` и описание "проверка ссылок недоступна в этой версии": тогда
  сервер не регистрируется по явному признаку, а не из-за побочного эффекта пустой
  переменной, и шаги не падают.

## 4. Tesseract и RapidOCR

Здесь честный ответ короткий: измерить я не смог, и часть вопроса остаётся открытой.

**Версия Tesseract на этом компьютере: не определена.** `tesseract --version` и
`where tesseract` в оболочке исполнителя не запускаются (см. 0.2), а в репозитории Довода
Tesseract не упоминается: это чужой контур, конвейер лежит в garant-bot. Владельцу это
стоит посмотреть одной командой:

```
tesseract --version
```

**Откуда брать сборку для поставки.** Официальных бинарных сборок под Windows проект
tesseract-ocr сам не выпускает; общепринятый источник - установщик от UB Mannheim
(github.com/UB-Mannheim/tesseract). Для поставки внутри установщика нужен не установщик, а
переносимая папка: ставится один раз на машине сборки, затем в артефакт копируются
`tesseract.exe` с его DLL и подпапка `tessdata` только с нужными языками. Перед этим
обязательно проверить в самой сборке, что она переносима (не требует записей в реестре) и
что лицензия сборки это допускает.

**Где rus.traineddata.** В репозиториях данных проекта: `tesseract-ocr/tessdata`,
`tessdata_best` (точнее, медленнее) и `tessdata_fast` (быстрее, менее точно). Какой из трёх
вариантов использует конвейер, по коду Довода определить нельзя, это настройка конвейера в
garant-bot. Выбор влияет и на размер поставки, и на время шага подготовки, поэтому его надо
зафиксировать осознанно, а не взять какой придётся.

**Лицензия.** Сам Tesseract под Apache 2.0. Для `rus.traineddata` и для конкретной
Windows-сборки лицензию надо брать из файлов, которые реально поедут в установщик, а не из
памяти: эти файлы и станут основой `THIRD_PARTY_NOTICES`. Утверждать лицензионный статус
того, чего я не видел, не буду.

**RapidOCR: какие ONNX-модели реально используются, поставляются или качаются, лицензии -
не установлено.** Это ровно те вопросы, ответы на которые лежат в
`garant-bot\dovod-tools` (конфиг RapidOCR и requirements) и в папке моделей. Что важно
знать заранее и проверить первым делом: RapidOCR по умолчанию **докачивает модели при
первом использовании** в папку своего пакета. Для цели 0.1.6 ("модели распознавания без
загрузки из интернета") это значит две вещи: модели должны лежать в поставке, и путь к ним
должен задаваться явно конфигом или переменной окружения, иначе на чистой машине без
интернета шаг подготовки упадёт, а с интернетом молча скачает модели в установочную папку и
сломает `checksums.json`. Отдельно проверить, есть ли среди используемых моделей
распознавание кириллицы: базовый набор RapidOCR ориентирован на китайский и английский, и
если кириллической модели в наборе нет, русский текст идёт через Tesseract, а роль RapidOCR
в конвейере другая (например детекция строк). Это меняет и состав поставки, и ответ про
лицензии моделей.

## 5. Выключение свободных инструментов агента

### 5.1. Нужный ключ: `tools.disabled`

Путь к коду:

- Схема настройки: `packages/cli/src/config/settingsSchema.ts:2827-2837`, ключ
  `tools.disabled`, тип массив, `requiresRestart: true`, слияние по объединению.
  Из описания: "Tool names hidden from the registry. Differs from permissions.deny:
  disabled tools are not registered at all, so they never appear in /tools and cannot be
  discovered by the model."
- Приём значения: `packages/core/src/config/config.ts:936` (`disabledTools?: string[]`),
  `2542` (инициализация), `6255-6259` (`getDisabledTools`).
- Применение: `packages/core/src/tools/tool-registry.ts:258-372`: инструмент не
  регистрируется ни как класс, ни как ленивая фабрика, учитываются и устаревшие имена-псевдонимы.
- Имена инструментов: `packages/core/src/tools/tool-names.ts:20-70`.

### 5.2. Чего делать нельзя: не `permissions.deny` на оболочку

Это главный вывод пункта. Команды `/dovod:*` работают через внедрение в запрос
(`!{...}`), и это внедрение **не идёт через инструмент оболочки**: обработчик
`packages/cli/src/services/prompt-processors/shellProcessor.ts:133-160` вызывает
`checkCommandPermissions` и `ShellExecutionService` напрямую. А
`checkCommandPermissions` (`packages/core/src/utils/shell-utils.ts:2111-2120`) на решение
`deny` возвращает `isHardDenial: true`, и `shellProcessor` такую команду не выполняет.

Отсюда: правило `permissions.deny` на `run_shell_command` выключило бы вместе с терминалом
и все семь команд Довода. А `tools.disabled` действует на уровне реестра инструментов, то
есть убирает терминал у модели, но внедрение `!{...}` в командах продолжает работать, если
соответствующее правило есть в `permissions.allow` (оно уже есть,
`dovod/settings.template.json:22-25`).

Также негодны устаревшие ключи: `tools.core`, `tools.allowed`, `tools.exclude`
(`settingsSchema.ts:2798-2826`) помечены Deprecated, причём описание `tools.core` прямо
говорит, что пустой список трактуется как отсутствие настройки и ничего не выключает.
Белый список инструментов строить на них нельзя.

### 5.3. Пример блока для settings.template.json

Шаблон по заданию не менялся. Это предложение для отдельного шага 0.1.6; перед применением
список надо сверить с `tool-names.ts` той версии, которая поедет в сборку, потому что имена
инструментов между версиями добавляются.

```json
"tools": {
  "disabled": [
    "run_shell_command",
    "edit",
    "write_file",
    "read_file",
    "glob",
    "grep_search",
    "list_directory",
    "notebook_edit",
    "web_fetch",
    "web_search",
    "agent",
    "skill",
    "workflow",
    "lsp",
    "enter_worktree",
    "exit_worktree",
    "cron_create",
    "cron_list",
    "cron_delete",
    "send_message",
    "create_sub_session",
    "monitor",
    "image_gen",
    "save_memory"
  ]
}
```

Что остаётся модели после этого: диалог, семь команд `/dovod:*` и встроенные служебные
инструменты (`todo_write`, `ask_user_question`, `structured_output`, `tool_search`),
которые к файлам дела и к терминалу доступа не дают. Файловых инструментов и терминала у
агента не остаётся: единственный путь к файлам дела - подкоманды `dovod_prompts`, то есть
сам конвейер, ограниченный папкой `для_модели`.

Две оговорки, которые надо проверить прогоном, а не чтением:

1. `tools.disabled` описан как управляемый маршрутом демона
   `POST /workspace/tools/:name/enable`, то есть список в принципе переключаем из
   интерфейса. Нужно убедиться, что в Доводе этот экран пользователю не доступен, иначе
   выключение формальное.
2. Снятие `read_file` и `glob` может повлиять на показ приложенных файлов и на подстановку
   `@файл` в интерфейсе. Это проверяется живым запуском, в оценке (пункт 7) заложено.

## 6. Остатки бренда Qwen на экранах пользователя

Все пути от корня репозитория. Разделено по тому, видит ли это пользователь.

### 6.1. Видно пользователю, надо править

| Где | Что |
| --- | --- |
| `packages/desktop-shell/dovod/commands/prepare.toml:1` | в описании команды: "по умолчанию текущая папка Qwen". Описание показывается в списке команд. |
| `packages/web-shell/client/i18n.tsx:10441` | русская строка `settings.models.runtimeSyncFailed`: "Перезапустите qwen serve". |
| `packages/web-shell/client/i18n.tsx:8515` | русская строка про рабочие процессы: "добавьте файл .js в .qwen/workflows". |
| `packages/cli/src/config/settingsSchema.ts:2084` | `label: 'Respect .qwenignore'`. Попадает на экран настроек в обход перевода, см. ниже. |
| `packages/cli/src/config/settingsSchema.ts` | всего 48 упоминаний Qwen в метках и описаниях настроек, в том числе пути `~/.qwen`. Все попадают на экран по тому же механизму. |

Механизм утечки английских строк схемы на русский экран: `SettingsMessage.tsx:150-171`
берёт перевод по ключу `settings.label.<путь>` или `settings.description.<путь>`, **а при
отсутствии ключа подставляет `setting.label` / `setting.description` из схемы как есть**.
Для `respectQwenIgnore` ключ переведён только в китайском блоке
(`i18n.tsx:6870-6872`); в русском блоке (строки 6908-10466) его нет, значит на русском
экране показывается английское "Respect .qwenignore". Это не одна строка, а целый класс:
любая настройка без русского ключа показывается английским текстом из схемы, а в схеме
бренда много.

### 6.2. Имя папки профиля

`~/.qwen` (на Windows `%USERPROFILE%\.qwen`). Код: `dovod/dovod-entry.js:32-47`
(`resolveQwenHome`, перебивка через `QWEN_HOME`). Папка сама по себе скрытая и на экранах
не показывается, но её имя попадает в текст: `env.template` (строки про `~/.qwen/.env`),
`dovod/README.md`, строки настроек из 6.1 и сообщения об ошибках с путями. Переименование
через `QWEN_HOME` технически возможно (например в `%APPDATA%\law.dovod.desktop`), но это
меняет расположение настроек у владельца, который уже пользуется 0.1.5, и требует переноса
существующего профиля. Решение продуктовое, не моё; в оценке заложено как отдельный пункт с
риском.

### 6.3. Не видно пользователю, править не нужно

Для полноты, чтобы следующий шаг не тратил на это время: `"qwen serve listening on"`
(`runtime.rs:20`) - разбор строки журнала демона, `runtime/qwen-code` - внутреннее имя
папки поставки, `name: '@qwen-code/qwen-code'` в `manifest.json`
(`prepare-runtime.js:106`) - метаданные сборки, ключи переводов вида `about.qwenCode`,
`agent.create.method.qwen`, `skilldesc.qwenCodeClaw` - имена ключей, значения в русском
блоке уже "Довод" (`i18n.tsx:6924`, `7712`, `8974`), `Qwen-Code-Desktop-*.zip` в
`desktop-release.yml:468, 515-516, 667-670` - только мост с Electron для macOS, в
Windows-сборке не участвует. Упоминания Qwen в `LICENSE`, `NOTICE` и в заголовках
изменённых файлов обязательны по Apache 2.0 и по CLAUDE.md §2, их не трогать.

## 7. Оценка оставшихся шагов 0.1.6

Часы - работа исполнителя, без ожидания сборок CI и без приёмки владельцем. Сроков не
называю: половина пунктов зависит от того, что найдётся в конвейере, которого я не видел.

| Шаг | Часы | Риск |
| --- | --- | --- |
| Разбор конвейера: точки входа, зависимости, состав моделей, requirements | 2-4 | Главная неизвестность всей версии. Если `dovod_prompts.py` вызывает `dovod_run.py` через `sys.executable`, заморозка требует правки конвейера в garant-bot, то есть работы в другом репозитории по его правилам. |
| Пробная сборка PyInstaller onedir, доведение до запуска | 4-10 | Разброс большой и сузить его чтением нельзя. onnxruntime и RapidOCR - типовой источник недостающих DLL и файлов данных, каждый круг "собрал, запустил, добавил hidden-import" стоит времени. |
| Фиксация моделей RapidOCR: положить в поставку, убрать докачку | 3-6 | Если кириллической модели в наборе нет, меняется состав поставки и, возможно, сам конвейер. Проверяется прогоном без интернета. |
| Tesseract: переносимая папка, tessdata, TESSDATA_PREFIX | 2-4 | Переносимость сборки под Windows надо подтвердить, а не предположить. |
| Правка prepare-runtime.js, tauri.conf.json, smoke-runtime.js под dovod-tools | 3-5 | Низкий: код скачивания, сверки и проверки целостности переиспользуется, образец на Node уже работает. |
| Workflow в garant-bot плюс скачивание по токену в desktop-release.yml | 3-5 | Средний: настройка прав токена и первый зелёный прогон обычно не с первого раза. Проверяется только живым запуском, то есть включением Actions. |
| Перевод команд `/dovod:*` с python на exe, автоподстановка DOVOD_TOOLS, правила permissions.allow | 2-4 | Средний: правила `permissions.allow` литеральные и без wildcard (ограничение режима AUTO), совпадение строки правила с фактической командой проверяется только запуском. |
| Сужение рабочей папки до `для_модели` в choose_workspace | 2-3 | Низкий по коду, но это изменение поведения экрана "Открыть дело", нужна сверка с владельцем. |
| Отключение проверки ссылок без падения шагов | 1-2 | Низкий: механизм отказа от регистрации MCP-сервера уже есть, нужен явный признак вместо побочного эффекта. |
| `tools.disabled` в шаблоне плюс проверка, что `@файл` и показ вложений не сломались | 2-4 | Средний: снятие `read_file` и `glob` может задеть интерфейс, выясняется прогоном. |
| Остатки бренда из 6.1 плюс русские ключи для настроек со схемными метками | 3-6 | Разброс из-за последнего: ключей в схеме много, объём зависит от того, сколько настроек реально видны на экранах Довода. |
| THIRD_PARTY_NOTICES из фактических файлов поставки | 2-3 | Низкий по труду, но делается после того, как состав поставки заморожен, иначе переделывать. |
| Сборка установщика в CI и приёмка по чеклисту CLAUDE.md §8 на чистой Windows 11 | 3-5 | Чистая машина обычно находит то, чего не видно на машине разработчика: отсутствующий VC++ runtime, SmartScreen, путь с кириллицей. |

Итого примерно 32-61 час работы исполнителя. Верхняя граница вероятнее нижней: три пункта
(разбор конвейера, сборка PyInstaller, модели RapidOCR) оцениваются вслепую, без доступа к
коду конвейера.

Два риска вне таблицы, которые могут поменять план версии целиком:

1. **Размер установщика.** Node (около 70 МБ после распаковки), Python с зависимостями,
   onnxruntime, модели ONNX, tesseract с tessdata. Правдоподобен итог в несколько сотен
   мегабайт. Если это неприемлемо, решение (какие модели убрать, какую точность потерять)
   принимает владелец, и чем раньше станет известна цифра, тем лучше. Цифру даст первая же
   пробная сборка.
2. **Неподписанный установщик.** `desktop-release.yml:344` при отсутствии сертификата
   выпускает unsigned и предупреждает про SmartScreen. Для 0.1.6 (только для владельца)
   это допустимо, для 0.1.7 (закрытый пилот) - нет. Сертификат стоит денег и времени на
   выпуск, запускать этот процесс надо заранее, а не в конце 0.1.7.
